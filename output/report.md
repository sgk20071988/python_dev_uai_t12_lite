## 1. Возникшие трудности и способы их решения

- Автоопределение кодировки на коротких текстах: charset-normalizer иногда ошибается при <50 байт. Решение — fallback UTF-8 → ISO-8859-1 → cp1251 → Latin-1, плюс запись source_encoding в JSON.
- Инверсия регистра и Unicode: str.swapcase() для ß даёт SS (по стандарту Unicode), а не ẞ. Для задачи приемлемо, но важно осознавать: регистр в Unicode — не всегда «одна буква в одну».
- Сохранение структуры в zip: zipfile.write по умолчанию кладёт только имя файла. Решение — явный arcname=path.relative_to(DATA_DIR.parent).as_posix().
- Проверка целостности: распаковка поверх data/ сравнивает файл с самим собой. Решение — восстановление в data_restored/ и сравнение по SHA-256.
- JSON Schema и format: по умолчанию jsonschema не проверяет format: date-time, нужен явный format_checker. Без него валидация дат «молча» проходит.
- st_ctime на Linux — inode change time, а не creation time. В реальном проекте лучше st_birthtime (где доступно) или platform-specific логика.

## 2. Выводы

- Сквозное логирование (logging) во всех модулях даёт воспроизводимость: по logs/project.log можно восстановить ход выполнения без перезапуска.
- Разделение «чтение/преобразование» и «сериализация» упрощает отладку: шаги можно перезапускать независимо.
- JSON Schema с additionalProperties: false — хороший контракт: при расширении FileInfo забыть обновить схему не получится.
- Единая точка запуска (run_all.py) с subprocess и perf_counter изолирует падения и упрощает проверку всего пайплайна одной командой.

## 3. Предложенные улучшения

- Вынести setup_logging в logging_config.py — сейчас он дублируется в каждом модуле.
- Хранить в FileInfo относительный путь (относительно PROJECT_ROOT) вместо абсолютного — артефакт не будет привязан к машине.
- Добавить проверку согласованности records_count и len(files) (инвариант приложения, не JSON Schema) — кастомная проверка после валидации.
- Git LFS для backups/ — zip-архивы быстро растят репозиторий.
