# Домашнее задание: файлы, пути, кодировки, сериализация данных

Описание работы скриптов проекта: что делает каждый скрипт, какие методы
использованы и как скрипты связаны между собой.

---

## Общая архитектура

Проект состоит из набора независимых скриптов, которые выполняются
последовательно и передают друг другу результаты через файловую систему.
Связь между скриптами — не через импорт и общее состояние, а через
артефакты: файлы в `data/`, `backups/`, `output/` и `logs/project.log`.
Это позволяет перезапускать любой шаг отдельно и отлаживать пайплайн по шагам.

Все пути централизованы в `config.py` (`PROJECT_ROOT` вычисляется от
расположения самого `config.py`, а не от текущей рабочей директории).
Это делает запуск скриптов независимым от cwd.

Все скрипты используют единый логгер `"project"`, который пишет
одновременно в `logs/project.log` (UTF-8) и в консоль. Формат записи:
YYYY-MM-DD HH:MM:SS | LEVEL | message

### Схема зависимостей


## `config.py`

**Назначение:** централизованные пути и настройки проекта.

**Что делает:**
- Вычисляет `PROJECT_ROOT` от расположения файла (`Path(__file__).resolve().parent`).
- Определяет пути к `data/raw`, `data/processed`, `logs/`, `backups/`, `output/`.
- Задаёт единый путь к лог-файлу `logs/project.log`.

**Использованные методы:**
- `pathlib.Path` — безопасная работа с путями (оператор `/` как join,
  корректные разделители на Windows/Linux/macOS).
- `Path(__file__).resolve()` — абсолютный нормализованный путь к файлу.
- `Path.parent` — родительская директория.

**Почему так:** строковая склейка путей ломается на Windows (обратные слэши)
и при запуске из другой директории. `pathlib` + вычисление от `__file__`
решают обе проблемы.

## `file_info.py`

**Назначение:** класс `FileInfo` — модель метаданных о файле, с сериализацией
в dict и десериализацией с валидацией.

**Что делает:**
- Хранит: имя файла, полный путь, размер в байтах, дату создания,
  дату последнего изменения.
- `from_path(path)` — фабрика: собирает `FileInfo` по объекту `Path`.
- `to_dict()` — сериализация в словарь (основа для JSON).
- `from_dict(data)` — десериализация с проверкой обязательных полей,
  типа `size_bytes` и формата дат (ISO 8601).

**Использованные методы:**
- `@dataclass` — автоматическая генерация `__init__`/`__repr__`/`__eq__`.
- `dataclasses.asdict()` — рекурсивное превращение dataclass в dict.
- `Path.stat()` — один системный вызов, даёт `st_size`, `st_mtime`, `st_ctime`.
- `Path.resolve()` — абсолютный путь.
- `datetime.fromtimestamp(...).isoformat(timespec="seconds")` — ISO 8601.
- `datetime.fromisoformat(...)` — парсинг и валидация даты при десериализации.

**Почему даты — строки ISO 8601:** `datetime` не сериализуется в JSON
«из коробки». ISO 8601 — стандарт, машиночитаем, человекочитаем и
валидируется в JSON Schema (`format: date-time`).

**Известное ограничение:** `st_ctime` на Linux — это inode change time,
а не дата создания файла. На Windows — creation time. Для учебной задачи
приемлемо; в реальном проекте — `st_birthtime` (где доступно) или
platform-specific логика.

## `task1.py` — Задание 1: структура директорий и файлы в разных кодировках

**Что делает:**
1. Создаёт дерево директорий: `data/raw`, `data/processed`, `logs`, `backups`, `output`.
2. Создаёт в `data/raw/` четыре текстовых файла:
   - `greeting_ru.txt`, `greeting_en.txt` — в UTF-8;
   - `greeting_de.txt`, `greeting_fr.txt` — в ISO-8859-1 (latin-1).
3. Пишет в `logs/project.log` записи о каждом шаге (с датой и временем).

**Использованные методы:**
- `Path.mkdir(parents=True, exist_ok=True)` — идемпотентное создание
  вложенных директорий: родители создаются, существующие не дают ошибку.
- `Path.write_text(text, encoding=...)` — запись строки в файл в заданной кодировке.
- `Path.stat().st_size` — размер файла в байтах.
- `logging.FileHandler(..., encoding="utf-8")` — лог всегда в UTF-8.
- `logging.StreamHandler` — дублирование лога в консоль.
- `logging.Formatter` с `asctime` — дата/время в каждой записи.

**Почему разные кодировки:** это нужно для Задания 2, где кодировка
определяется автоматически по байтам. Наличие файлов в ISO-8859-1
(с байтами > `0x7F`) делает задачу автоопределения осмысленной.

**Почему `exist_ok=True`:** повторный запуск скрипта не должен падать.
Идемпотентность — базовое свойство скриптов, которые могут запускаться
многократно.

## `task2.py` — Задание 2 (часть 1): чтение, определение кодировки, инверсия регистра

**Что делает:**
1. Читает все `*.txt` из `data/raw/` как сырые байты.
2. Определяет кодировку каждого файла.
3. Декодирует текст и инвертирует регистр (`swapcase`).
4. Пишет результат в `data/processed/` с суффиксом `_processed`, всегда в UTF-8.

**Использованные методы:**
- `Path.read_bytes()` — чтение сырых байтов (кодировку определяем сами).
- `charset_normalizer.from_bytes(...).best().encoding` — статистическое
  определение кодировки (современная замена `chardet`).
- Fallback-перебор: `utf-8` → `iso-8859-1` → `cp1251`. Первая успешная
  декодировка без `UnicodeDecodeError` считается ответом.
- `str.swapcase()` — Unicode-корректная инверсия регистра.
- `Path.write_text(..., encoding="utf-8")` — processed всегда в UTF-8.

**Почему сначала байты, а потом декодирование:** `read_text()` пришлось бы
вызывать с уже известной кодировкой. Но мы её не знаем — её надо определить
по байтам. Поэтому `read_bytes()` → detect → decode.

**Почему processed всегда в UTF-8:** это «внутренний» формат проекта.
Унификация упрощает следующий шаг — JSON-сериализацию (JSON всегда в UTF-8).

**Нюанс Unicode:** `"ß".swapcase() == "SS"` по стандарту Unicode, а не `"ẞ"`.
Это не баг, а корректное поведение `swapcase` для этой буквы.

## `task2_serialize.py` — Задание 2 (часть 2): JSON с исходным и преобразованным текстом

**Что делает:**
1. Для каждого `*_processed.txt` в `data/processed/` находит исходный файл
   в `data/raw/` (`greeting_de_processed.txt` → `greeting_de.txt`).
2. Читает оригинал в его исходной кодировке и processed в UTF-8.
3. Собирает записи: имя файла, `source_encoding`, `original_text`,
   `processed_text`, `size_bytes`, `last_modified`.
4. Пишет всё в `output/processed_data.json`.

**Использованные методы:**
- `Path.glob("...")` — поиск файлов по шаблону.
- `str.removesuffix("_processed")` — восстановление имени оригинала.
- `json.dumps(..., ensure_ascii=False, indent=2)` — читаемый JSON,
  кириллица сохраняется как есть (не `\uXXXX`).
- `datetime.fromtimestamp(st_mtime).isoformat()` — дата изменения в ISO 8601.
- Переиспользование `detect_encoding` из `task2.py` (импорт функции).

**Почему `ensure_ascii=False`:** иначе кириллица и умлауты превратятся
в `\uXXXX`, файл станет нечитаемым глазами и неудобным для проверки.
JSON-стандарт разрешает UTF-8 напрямую.

**Почему отдельный скрипт от `task2.py`:** разделение «преобразование» и
«сериализация» позволяет перезапускать шаги независимо и даёт чистые
тайминги в `run_all.py`.

## `task3_backup.py` — Задание 3 (часть 1): zip-архив `data/`

**Что делает:**
1. Рекурсивно собирает все файлы из `data/`.
2. Создаёт `backups/backup_YYYYMMDD.zip` с сохранением структуры папок
   (внутри архива пути вида `data/raw/greeting_ru.txt`).

**Использованные методы:**
- `zipfile.ZipFile(path, "w", compression=ZIP_DEFLATED)` — запись с сжатием.
- `zf.write(path, arcname=...)` — `arcname` задаёт путь внутри архива.
- `Path.rglob("*")` — рекурсивный обход директории.
- `Path.relative_to(...).as_posix()` — относительный путь с прямыми слэшами
  (переносим между ОС).
- `datetime.now().strftime("%Y%m%d")` — дата в имени архива.

**Почему явный `arcname`:** без `arcname` `zipfile.write` кладёт только имя
файла — структура папок в архиве теряется, и при распаковке все файлы
лягут в один каталог.

**Почему перезапись при совпадении имени:** имя содержит только дату
(как в задании). При повторном запуске в тот же день архив перезаписывается —
предсказуемое поведение.

## `task3_restore.py` — Задание 3 (часть 2): восстановление и проверка целостности

**Что делает:**
1. Находит самый свежий `backup_*.zip` (по `mtime`).
2. Проверяет CRC всех файлов в архиве (`zf.testzip()`).
3. Распаковывает архив в `data_restored/` (отдельная директория!).
4. Побайтово сравнивает `data/` и `data_restored/data/` по SHA-256.
5. Логирует результат: совпадение или расхождения (с указанием файлов).

**Использованные методы:**
- `zipfile.ZipFile.testzip()` — проверка CRC; возвращает имя битого файла или `None`.
- `zf.extractall(dir)` — распаковка с сохранением структуры.
- `hashlib.sha256` + чтение блоками по 64 КиБ — побайтовое сравнение
  без загрузки файлов целиком в память.
- `shutil.rmtree` — очистка `data_restored/` перед повторной распаковкой.
- Множества относительных путей — поиск «только в исходнике»,
  «только в восстановленном», «в обоих».

**Почему восстановление в `data_restored/`, а не в `data/`:** если распаковать
поверх `data/`, сравнение «восстановленного» с исходным превращается
в сравнение файла с самим собой — проверка теряет смысл. Отдельная
директория позволяет честно сравнить два дерева.

**Две независимые проверки:**
1. `testzip()` — целостность архива (CRC). Ловит повреждения zip-файла.
2. SHA-256 — целостность данных после распаковки. Ловит любые расхождения
   содержимого, даже если архив формально цел.

## `task4_serialize.py` — Задание 4 (часть 1): `FileInfo` → JSON

**Что делает:**
1. Собирает `FileInfo` по всем файлам `data/processed/` (рекурсивно).
2. Сериализует в `output/processed_files_info.json`:
   `generated_at`, `records_count`, `files[]`.
3. Демонстрирует round-trip: читает JSON обратно и восстанавливает
   объекты `FileInfo` через `from_dict` (с `assert`-проверкой типов).

**Использованные методы:**
- `FileInfo.from_path(path)` — фабрика из `file_info.py`.
- `FileInfo.to_dict()` — сериализация через `dataclasses.asdict()`.
- `FileInfo.from_dict(...)` — десериализация с валидацией.
- `json.dumps(..., ensure_ascii=False, indent=2)` — читаемый JSON.
- `Path.rglob("*")` — рекурсивный обход.

**Почему отдельный JSON от `processed_data.json`:** `processed_data.json`
(Задание 2) — содержимое файлов (тексты). `processed_files_info.json`
(Задание 4) — метаданные (размеры, даты, пути). Это разные сущности,
смешивать их в одном файле не стоит.

**Зачем round-trip в самом скрипте:** требование задания — «убедиться, что
при десериализации данные восстанавливаются корректно». Явная проверка
`to_dict` → JSON → `from_dict` делает это утверждение проверяемым,
а не декларативным.

## `task4_validate.py` — Задание 4 (часть 2): JSON Schema и валидация

**Что делает:**
1. Сохраняет JSON Schema в `output/processed_files_info.schema.json`
   (рядом с данными — удобно версионировать и переиспользовать).
2. Проверяет, что сама схема валидна (`Draft202012Validator.check_schema`).
3. Валидирует `processed_files_info.json` по схеме.
4. Печатает отчёт: для каждой ошибки — путь до проблемного места
   и сообщение. При отсутствии ошибок — сообщение об успехе.

**Использованные методы:**
- `jsonschema.Draft202012Validator` — валидатор стандарта JSON Schema 2020-12.
- `Draft202012Validator.check_schema(SCHEMA)` — проверка корректности схемы.
- `validator.iter_errors(instance)` — итератор всех ошибок (не только первой).
- `format_checker=...FORMAT_CHECKER` — включает проверку `format: date-time`
  (по умолчанию `jsonschema` `format` **не** проверяет!).
- Сортировка ошибок по `absolute_path` — детерминированный порядок вывода.

**Структура схемы:**
- `$defs/file_info` — переиспользуемое определение одного `FileInfo`.
- `required` — обязательные поля.
- `additionalProperties: false` — запрет лишних полей (контракт строгий).
- `format: date-time` — проверка ISO 8601 (только с `format_checker`).
- `minimum: 0` для `size_bytes` — размер не может быть отрицательным.

**Почему `check_schema` перед валидацией:** опечатка в схеме (`"typ"` вместо
`"type"`) иначе приведёт к «фантомным» ошибкам валидации, которые трудно
отладить. `check_schema` ловит это сразу.

**Почему отчёт по всем ошибкам, а не по первой:** `iter_errors` даёт все
несоответствия за один проход — удобнее для исправления, чем запускать
валидатор N раз.

## `task5_report.py` — Задание 5: итоговый отчёт (Markdown + PDF)

**Что делает:**
1. Строит `Report` (модель из `report_model.py`) с тремя разделами:
   трудности и решения, выводы, предложенные улучшения.
2. Рендерит в `output/report.md` (через `render_markdown`).
3. Рендерит в `output/report.pdf` (через `reportlab`).
4. При отсутствии `reportlab` — генерирует только Markdown и пишет ERROR в лог.

**Использованные методы:**
- `report_model.Report` / `render_markdown` — единая модель, два рендерера.
- `reportlab.platypus.SimpleDocTemplate` — сборка PDF из «потока» элементов.
- `Paragraph`, `Table`, `TableStyle`, `Preformatted` — элементы PDF.
- `pdfmetrics.registerFont(TTFont(...))` — подключение TTF с кириллицей
  (`DejaVuSans` на Linux, `Arial`/`Calibri` на Windows, `Arial` на macOS).
- `ParagraphStyle` — стили (заголовки, тело, ячейки, код).

**Почему единая модель для MD и PDF:** если писать Markdown и PDF отдельно,
они разойдутся. Модель `Report` гарантирует, что оба формата содержат
одно и то же.

**Почему поиск шрифта:** `reportlab` по умолчанию использует Helvetica,
в которой нет кириллицы — русский текст превратился бы в `"?"`. Скрипт ищет
TTF с кириллицей в стандартных путях ОС и явно регистрирует его.

**Почему fallback на Markdown:** если `reportlab` не установлен — лучше
отдать валидный `.md`, чем упасть целиком. PDF — «улучшение», а не
единственный результат.

## `report_model.py` — модель отчёта и Markdown-рендерер

**Назначение:** описывает отчёт как список типизированных блоков
(`h1`, `p`, `bullets`, `table`, `code`) и рендерит его в Markdown.
PDF-рендерер (в `task5_report.py`) использует ту же модель.

**Использованные методы:**
- `@dataclass ReportBlock(kind, payload)` — один блок отчёта.
- `@dataclass Report(title, subtitle, blocks)` — отчёт целиком.
- Fluent API: методы `h1`/`p`/`table`/... возвращают `self` для цепочек вызовов.
- `field(default_factory=list)` — корректный mutable default для `blocks`.

**Почему так:** один источник данных → несколько форматов вывода (MD, PDF).
Легко добавить третий (HTML) без переписывания содержания отчёта.

## `scripts_overview.py` — генератор этого файла

**Что делает:** пишет `README.md` в корне проекта — общее описание работы
всех скриптов, использованных методов и связей между скриптами.

**Использованные методы:**
- Тройные кавычки для многострочного текста (без экранирования).
- `Path.write_text(text, encoding="utf-8")` — запись в UTF-8.
- `datetime.now().isoformat()` — метка генерации.

**Зачем генератор, а не ручной файл:** документ воспроизводим — его можно
перегенерировать после изменений в скриптах. Это артефакт, а не «забытый»
файл в репозитории.

pip install -r requirements.txt
